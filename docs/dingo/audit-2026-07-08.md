### H1. ingest_file inserts the files row and per-track rides rows without a transaction, so a mid-ingest failure permanently and silently loses tracks on retry
**`crates/ingest/src/service.rs:102`** — found by: ingest-core

*Verifier:* Confirmed: repository.rs insert_file (fetch_optional(pool), line 35) and insert_ride (execute(pool), line 109) each autocommit on the pool with no transaction anywhere in the crate; service.rs commits the files row (line 89) before the fallible insert_ride loop (lines 102-104), and on retry file_exists_by_hash (line 64) returns was_duplicate=true with zero ride_ids, so never-inserted tracks are permanently skipped. No orphan/partial-ingest repair path exists anywhere in the workspace, and all callers (zip.rs, cli/main.rs, organize.rs) treat was_duplicate as success — in bulk zip ingest the original failure is one warn! line. Reachable via a connection drop or a PostGIS geometry error mid-loop during realistic bulk ingestion; the raw file survives on disk so it is high (silent wrong results in the source-of-truth DB) rather than critical unrecoverable loss.

### H2. File store writes directly to the final content-addressed path with no temp-file+rename, so a partial write poisons the store permanently
**`crates/ingest/src/file_store.rs:102`** — found by: ingest-core

During store()/store_bytes(), fs::write to `{hash}.{ext}` is interrupted (process kill, power loss, ENOSPC — fs::write leaves the truncated file behind on error). The truncated file now sits at the content-addressed path but its bytes do not match its hash name. Every subsequent store of the same content hits `dest_path.exists()` (line 97/136) → was_duplicate=true → the copy is skipped forever, so the corrupted raw archive file (the system's source-of-truth raw recording) is never repaired, and FileStore::read returns garbage for that hash.

*Verifier:* file_store.rs lines 102 and 139 call fs::write directly on the final `{hash}.{ext}` path with no temp-file+rename, and the dedup checks at lines 97/136 use only dest_path.exists() with no content verification — so a truncated file left by a kill/power-loss/ENOSPC mid-write is treated as a valid duplicate forever, and FileStore::read (line 165) returns the corrupt bytes with no repair path. The scenario is realistic (interrupting a bulk ingest and re-running it), and no caller guards against it: service.rs:57-73 treats the exists-hit as success. Severity high is correct (not critical) because ride parsing uses the source file's bytes, so DB rides stay correct and the original file usually survives outside the store — the poisoning is confined to the raw archive copy.

*Verifier:* smooth.rs lines 49-80 compute the window mean including the point under test, then replace any point >50 m from that mean with the mean itself; a 300 m spike shifts every 5-point mean containing it by ~60 m, so each accurate neighbour exceeds the threshold and is replaced by the spike-contaminated average, spreading ~60 m of error across five points instead of removing the outlier.

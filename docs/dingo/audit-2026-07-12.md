Adversarially-verified workflow audit of everything merged since the
2026-07-08 audit (baseline `c108471`): the export crate, basket/export/share
pipeline, privacy zones, web import, route drawer + grades, Strava sync, and
the parallel-session harvest/Strava-heat subsystem. 9 subsystem finders → 42

**Headline: the privacy feature's geometry trim is correct, but private
location data leaks *around* it in several ways, and `/api/export/share` is
remotely triggerable. These should be fixed before any hosted/shared use.**

---

## HIGH

### H1. `/api/export/share` is an unauthenticated, CORS-open exfiltration endpoint
`crates/daemon/src/routes/export.rs:467`
The daemon has no auth on any `/api` route and sends permissive CORS
(`allow_origin(Any)`). While the daemon runs, **any web page the user visits**
can `fetch('http://localhost:3000/api/rides')` to enumerate ride ids, then POST
`/api/export/share` — the daemon publishes the user's tracks to a public-readable
gist and returns the URL in a CORS-readable body. Zero interaction beyond
visiting a page. (Geometry is zone-trimmed, so home is masked, but the whole
route corpus leaks to a durable public URL.) This is the most serious finding.
*Fix direction:* require a local token / same-origin check for mutating +
share endpoints, or bind share behind an explicit confirmation; at minimum
tighten CORS to the known web origin.

### H2. Ride names leak the hidden suburb on every export
`crates/daemon/src/routes/export.rs:600`, `crates/export/src/lib.rs:286`
1,066 of 1,133 zone-sensitive rides are named `"Arcadia to …"` / `"Arcadia loop
via …"`. The name ships verbatim in GPX `<name>` tags, filenames, bundle
manifests, and the share gist's bundle.json — defeating the geometry trim.
Worst case: a **fully-private** ride (geometry 100% suppressed) still puts its
name in the `skipped[]` array published inside the link-readable gist,
announcing `"Arcadia loop 2 kms"` to any link holder. *Fix direction:* scrub
zone suburb tokens from exported names/filenames for sensitive rides, and drop
(or anonymize) names in the shared `skipped[]` list.

### H3. Adding a privacy zone doesn't re-trim already-exported library files
`crates/cli/src/organize.rs:246` (also 289; 3 finders independently)
`export_tree` is incremental: a ride whose `exported_path` file exists is
skipped (or merely relocated) without regenerating content, unless `--force`.
Every ride exported before the privacy feature existed keeps its full home
geometry on disk after `privacy add-place` + `organize` — including
now-fully-private rides. Yet the CLI prints *"their exports will be trimmed"*.
The synced library folder keeps leaking after the user believes it's redacted.
*Fix direction:* privacy add/remove should force-regenerate affected rides (or
`organize` should detect zone-vs-file staleness), and the message should not
over-promise. (The "will be trimmed" count is also wrong — it counts all
intersecting rides, but only start/end-inside rides are trimmed.)

### H4. Organize plants raw untrimmed copies inside the library tree
`crates/cli/src/organize.rs:559`
Phase 4 moves the original source file into `<dest>/Duplicates/` (loose) or
`<dest>/Archives/` (zips) — full resolution, home points included — inside the
same library tree the privacy contract calls a trimmed egress surface. A ride
whose `Recorded/` GPX was trimmed (or fully excluded) still has its complete
raw track sitting in `Duplicates/`. Leak materializes if the whole library
root is synced/shared. *Fix direction:* keep the raw staging folders outside
`--dest`, or trim/exclude sensitive raws too, or document Duplicates/Archives
as never-sync.

### H5. Route drawer crashes (white screen) after a zoom-tier change mid-draw
`web/src/components/Map/MapView.tsx:1000`
`lastSnapRef` stores a vertex **index** into the ride path at the current zoom
tier. `useRides` refetches at a different simplification tier across zoom 11/15,
so the same ride's array gets a different length. Snap on ride R at z15, zoom
out below z11, click R again → the follow-splice loop reads `path[699…60]`,
pushes ~640 `undefined` into `drawPath`, and the next render destructures
`undefined` → TypeError. No ErrorBoundary exists, so React unmounts → white
screen, in-progress route lost. The other tier direction silently saves a
**wrong** plan geometry. (I suspected this in the audit prompt; confirmed.)
*Fix direction:* store snapped lon/lat (+ tier stamp), re-resolve the index
against the current path, drop follow-continuity when geometry identity changed.

## MEDIUM

- **M1. DingoNav corridor bbox uses untrimmed geometry** (`export.rs:699`) —
  `selection_bbox` = `ST_Extent(cleaned_geometry)`; a home-start ride puts the
  home corner into the basemap PMTiles bounds and the z15 Strava-tile corridor
  shipped in the bundle, recoverable by adding back the known 0.015° pad. Even
  for a fully-private ride. *Fix:* compute the bbox from zone-differenced
  geometry like `dingonav_heat_features` already does.
- **M2. `/api/export` `prune_stale` can delete foreign files** (`export/src/lib.rs:539`) —
  no ownership check before recursively deleting non-written `.gpx` under the
  bundle dir; naming a bundle after an existing synced folder (OsmAnd's `rec`)
  wipes real recordings, and it follows symlinks out of the tree. *Fix:*
  require a Dingo manifest / empty dir before pruning; don't traverse symlinks.
- **M3. PATCH commits mode before validating grade** (`rides.rs:707`) —
  `{mode:"mtb",grade:9}` writes the mode (+ `mode_source='user'`, blocking
  future auto-reclass) then 400s on grade, so an error response hides a
  persisted write. *Fix:* validate both, then update in one transaction.
- **M4. DingoNav/share panics on a NULL-named ride** (`export.rs:584`) —
  `dingonav_tracks` does `r.get::<String>("name")` with no COALESCE; a
  web-imported ride whose naming failed (NULL name) drops the connection on
  every export containing it. *Fix:* read as `Option<String>` (as build_bundle
  does).
- **M5. Strava tile cap not enforced at a single zoom** (`export.rs:845`) —
  `while total>cap && by_zoom.len()>1` stops at one zoom even if it's tens of
  thousands of tiles; "Select all" + include_strava → ~40k sequential
  authenticated Strava fetches from your account. *Fix:* cap absolutely, or
  reject over-wide corridors.
- **M6. Strava sync: no rate-limit handling** (`strava_sync.rs:241`) —
  default `--limit 200` blows the 100-req/15-min quota ~activity 95; the 429
  aborts before clean/name, leaving imports raw. *Fix:* backoff + Retry-After,
  and run clean/name in a `finally`-style block.
- **M7. Strava sync: failed activity is skipped forever** (`strava_sync.rs:188`) —
  the watermark = max(started_at) advances past a transiently-failed activity
  on the next run → permanent silent gap. *Fix:* track a low-water mark or
  record failures.
- **M8. Zip source-tag watermark mistags concurrent imports** (`organize.rs:483`) —
  `UPDATE … WHERE imported_at >= mark AND source IS NULL` sweeps up any ride
  ingested (web import, `dingo ingest`, strava) during the zip run; host-clock
  vs Postgres-`now()` drift also mis-windows. *Fix:* tag by the ride ids the
  zip actually produced (needs ingest_zip to return them), not a time window.
- **M9. Mode PATCH doesn't invalidate `allRideMeta`** (`DetailPane.tsx:102`) —
  Places tree keeps stale type/counts (and folder-click selects the stale set)
  for up to 5 min after a mode change; the grade paths *do* invalidate it, so
  it's an omission. *Fix:* add `allRideMeta`/`rideLocations` to the mode
  invalidations.
- **M10. Heat overlay raster source has no `maxzoom`** (`MapView.tsx:767`) —
  MapLibre requests z14+ tiles the harvester never produced (max z13/14) → the
  blue "everyone else" heat blanks out exactly at trail-inspection zoom. *Fix:*
  set the source `maxzoom` to the archive max so MapLibre overzooms.

Dingo — Architecture & Design

A local-first, segment-centric trail knowledge system for off-road riding. Segments — not GPX files — are the source of truth, scored per direction, mode, and condition.

Rust workspace PostGIS React + deck.gl sqlx MapLibre GL Reviewed 2026-06-22 against code
Status legend: Built shipped & working in code Partial exists but stubbed / TODO Planned spec-only, not started
This document is largely a forward-looking vision. The diagrams below mark what is real today vs. aspirational. As of 2026-06-22 the full ingest → score pipeline works via CLI; the entire photos / ML / vector-search half of the spec is unbuilt.

01 System Architecture

A Rust workspace of 11 crates: a shared library layer, two runtimes (daemon & CLI), and two stubs (google, vision). The web UI talks to the daemon over HTTP; the CLI and daemon both connect directly to PostGIS.

02 The Processing Pipeline

Raw ride history is turned into a scored trail network through a fixed sequence of stages. The first seven stages are fully built and runnable today; the photo/ML tail is entirely planned.

Reality vs. spec — orchestration. The doc describes an event-driven bus (Postgres LISTEN/NOTIFY, an outbox table, a file watcher, and a chain ride_ingested → ride_cleaned → … → photos_analysed). None of that is built. Today the pipeline is CLI-stage-driven: you run dingo ingest, then clean, enrich, graph, match, stats, score as explicit commands. The event bus is the planned future.
Graph stage is Partial. Segment build exists, but the daemon's create_segment consensus-geometry algorithm is a TODO. The project has also pivoted from automatic graph building to user-defined segments (drawn in the UI from selected runs) — see §06.

03 Data Model

PostGIS holds 22 migrations. The ride/segment/run/stats core is fully built; every photo, POI, ML, and queue entity from the spec has no table yet.

Built entities Built

areas files rides routes segments segment_dirs runs segment_dir_stats segment_dir_dingo_score

Migrations cover speed, time-stats, HR, stopped-variance, feature-extraction, out_and_back, unreviewed-visibility, fit-metadata, name-metadata, multi-res geometry (z10/z14), the ride_mode enum, and a restructured stats + scores layout.

Spec entities with no table Planned

photos photo_labels pois poi_suggestions ml_training_queue rematch_queue

The spec lists all of these as "core entities". None exist in migrations. Vector search (LanceDB segment_embeddings / photo_embeddings) is likewise unbuilt.

04 Dingo Scoring Built

The score is a weighted sum of normalised features (0–100), computed per (segment_dir, mode, condition, profile). Four profiles weight features up (green) or down (red).

Feature extraction (length, grade, twistiness, pace_vs_shape, stop_density, hr_intensity) and all four profiles are implemented in the stats crate and runnable via dingo score rebuild. Note: surface/obstacle features that depend on photos are deferred — those inputs are zero until the photo pipeline exists.

Doc bug "MVP Build Order" lists Phase 1–5 Phase 3, 4, 5 each appear twice with duplicated numbering — see corrected roadmap §05 Doc fix
Bottom line. The "trail knowledge from rides" half of Dingo — ingest, clean, enrich, segment build, run match, stats, and Dingo scoring — is real and works end-to-end via CLI. The "photo intelligence" half — Google Photos, ML vision, POIs, vector search — and the event-driven orchestration remain entirely on the drawing board.

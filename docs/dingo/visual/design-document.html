A trail knowledge system
built from fourteen years of dirt.

Dingo is a local-first, segment-centric knowledge base for off-road riding. GPX and FIT files are raw material, not the product: rides are matched against a directed trail network and every segment accumulates stats, scores, photos, and conditions — per direction, per riding mode.

01

Why segments, not files

The core design position everything else follows from.

Every GPS platform treats the activity file as the atom: a ride is a row, and knowledge about a trail is smeared across hundreds of rows that happen to overlap it. Dingo inverts this. The atom is the segment — a stretch of trail between decision points — and each segment exists twice, once per direction, because a hill climbed and a hill descended are different trails in every way that matters.

Everything the system does is in service of that inversion:

  • Rides are evidence. A ride is decomposed into runs — traversals of directed segments — and its speed, heart-rate, timing, and photos are attributed to the segments it touched.
  • Stats live per (direction, mode, condition). An enduro bike, an MTB, and an ADV bike on the same track are three different datasets. Scoring (the Dingo score) is computed per riding mode.
  • Local-first. The corpus is personal GPS history and photos. Everything runs on one machine: PostGIS in Docker, a Rust daemon, a Vite dev server. No cloud dependency in the core loop.

Build constraint worth knowing

sqlx uses compile-time-checked queries against a live DATABASE_URL, and the offline cache is gitignored — so cargo build requires PostGIS running. Migrations are embedded at compile time: after adding one, rebuild the daemon before expecting it to apply.

04

Data model

Seven tables carry the design. Arrows read “feeds” or “belongs to”.

The units convention — read before touching speed

runs.speed_avg is m/s (the fast-path backfill convention). segment_dirs.speed_avg is km/h (fed by the graph builder’s whole-ride average × 3.6). The daemon presents km/h to the UI. The match crate converts at the boundary. One latent mismatch remains in point_matcher::calculate_score — documented, fix when touched (§09).

Ride → segment matching

Two deliberate paths with opposite trade-offs, plus the problem speed has to solve next.

fast pathslow path
Invocationdingo match --all --fastdingo match --ride | --area
MechanismOne SQL pass: each unmatched ride → its closest segment (Hausdorff, ≤50 m), one whole-ride runEvery point matched to the nearest segment within 30 m (lateral join), consecutive same-segment points become runs (min 5 points)
Timing / statsBackfilled from ride-level aggregates (whole-ride runs only)Computed per run from the cleaned time series: elapsed, stopped, moving, speed avg/max/variance, HR, start/end times
Speed awarenessnonenone yet — distance-only picking
CostSeconds for the whole corpusPer-ride; used for precision work
Post-passOut-and-back detection pairs opposing-direction runs on the same segment (attempted-climb heuristic via stop ratio)

Both paths converge on the same runs table, and as of 3 July both produce complete timing — the slow path previously wrote NULL speeds (a hardcoded speed: None) and never set start/end times; fixed and verified.

The parallel-trail problem

On enduro rides, singletrack often runs parallel to — and criss-crosses — the fire trail it feeds off. Both live inside the same 30 m matching corridor, so distance alone cannot separate them, and they must never merge into one segment: merged stats are meaningless. Speed is the discriminator.

06

Photos: the Takeout pivot

Phase 2 was designed for an API that no longer exists. The replacement is better.

The original design assumed OAuth read access to the Google Photos library — search by date range, download by URL. Google removed those API scopes on 31 March 2025; third-party apps can now only read content they themselves uploaded, and the replacement Picker API returns no location data and no permanent link to the original.

The pivot: Google Takeout archives. Their JSON sidecars carry exactly what the live APIs can't — geoData (lat/lng) and a permanent photos.google.com URL. So the storage model is low-res local, full-res linked:

Thumb · 200 px

~11 KB JPEG, content-addressed photos/{sha256}_thumb.jpg. List views, map dots, photo strips.

Medium · 800 px

~70 KB JPEG, same store. The hover card — enough resolution to read terrain.

Original · full res

Never stored. One click out to Google Photos via the sidecar’s permanent URL.

Import (crates/google/takeout.rs)

  • Walks an extracted archive, pairing media with sidecars — including the .supplemental-metadata.json variants, Takeout’s truncated names, and the IMG(1).jpg ↔ IMG.jpg(1).json duplicate quirk.
  • EXIF fallback when sidecars are missing; EXIF orientation applied so thumbnails aren’t sideways; HEIC decoded via macOS sips; videos and -edited renditions skipped; sha256 dedupe makes re-imports free.
  • Treats Takeout’s (0.0, 0.0) geoData as “no location” — it isn’t a real coordinate.

Matching (crates/google/photo_match.rs)

07

The web UI

One map, three overlays, two side panes. MapLibre renders the world; deck.gl renders the knowledge.

Rides layer

Mode-coloured paths (ADV orange, enduro crimson, MTB green, water aqua). Zoomed in: per-point HR / speed gradients with user-tunable colour boundaries. Two-tier filtering — hidden vs greyed — shared with the list.

Segments layer

The trail network as light lines; click to select (cyan), detail pane shows length, runs, grade, elevation, photos. The list’s Segments tab was a dead stub until July — it now drives the same selection.

Photos layer

White line-width dots; shots within ~11 m group into one dot with a count badge. Hover: 320 px card with pager, timestamp, and full-res link-out. Strips repeat in ride/segment detail panes.

  • Selection tools: click, shift-multi-select, freehand lasso (PostGIS polygon query), focus mode, auto-zoom. Ride and segment selections are mutually exclusive.
  • Filters: mode toggles, has-HR / has-speed, date range, and range sliders (HR, speed, distance) applied per-point on gradients.
  • Graph pane: elevation / speed / HR profiles over distance or time for the selection. Stats bar: corpus totals + selection summary.
  • Bulk workflows: ride type override (single or whole selection, marked as user override so reclassification never touches them).
  • Shareable views: map state lives in the URL hash and survives reload.

08

Decision log

Choices that will outlive the code that implements them.

decisionrationale
Segments over filesTrail knowledge should accumulate on the trail, not the recording. Directed segment_dirs because climb ≠ descent.
Per-mode everythingStats and scores keyed by riding mode — an MTB descent and an ADV descent are different facts about the same dirt.
Takeout over Photos APIForced (scopes removed Mar 2025) but strictly better: geo + permanent link-out that no current API provides. Picker API reserved for incremental top-ups.
Low-res local, full-res linked~80 KB per photo locally; originals stay in Google Photos one click away. Local-first without duplicating a photo library.
Content-addressed storesBoth raw ride files and photo renditions keyed by sha256 — dedupe is free, re-imports are idempotent.
Two matching pathsFast whole-ride SQL for corpus-scale iteration; slow point-level for precision. Same runs table, interchangeable.
Compile-time-checked SQLsqlx query checking against live PostGIS trades build friction for schema drift caught at compile time — twice this week the drift was caught at runtime instead, in the two handlers using unchecked queries (§09).
Ride data outside the repoPersonal GPS traces + multi-GB archives live in ~/Desktop/Projects/Dingo-data/; the repo carries 5 small GPX fixtures only.
Practice area workflowCentral Coast (384 rides) as the fast iteration loop; Australia-wide rebuilds are the slow full pass.

The through-line

Every horizon feeds the same loop: more evidence → better-shaped segments → richer per-mode knowledge. The July work (run timing, photos, working segments UI) closed the loop end-to-end for the first time — from a FIT file on a handlebar GPS to a scored, photographed, clickable segment on the map.

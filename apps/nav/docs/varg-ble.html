DingoNav ↔ Stark Varg EX

BLE telemetry integration — 2025 Varg EX · Arkenstone phone · read-only, display only. Rev 2, 28 July 2026.
Rev 2: the protocol is no longer guesswork. Layouts below are cross-checked against two working open-source clients — svag-mini (ESP32 firmware, verified on real MX/EX/SM) and stark-varg-garmin-bridge — and against the STATUS_BITS words VargPilot re-serves, which we confirmed live on the '25 EX. Remaining unknowns are flagged TBD.

Architecture

Connection flow

  1. requestDevice with acceptAllDevices — the VCU advertises neither its custom services nor a "Stark" name, so no filter can find it. The rider picks the bike's 17-char VIN from the list (one-time chore; getDevices() reclaims silently forever after). All three services must be in optionalServices or Chrome walls them off post-connect.
  2. Bonding is MITM + Secure Connections → a 4-digit PIN is mandatory. It's derivable from the VIN (garmin-bridge): SHA-256(VIN + "-19700101"), four digit-extractions → PIN. Since the advertised name IS the VIN, DingoNav shows the rider the expected PIN before Android asks.
  3. gatt.connect() (untimed — resolves when the bike powers on in range) → subscribe battery first (forces the bond exactly once) → then map + status, best-effort.
  4. startNotifications() only — never readValue() (returns nothing on this VCU).
  5. Watchdogs from link-up: a stall in the pair stage is almost always the buried Android PIN dialog — nudge at 20 s, abort to retry at 60 s. Drops auto-retry with backoff (1→15 s).
  6. Decode notifications → HUD. First 5 raw battery frames still logged as a sanity check against the layouts below.

The overlay is driven only by VCU state notifications — it fires when reverse actually engages (after the bike’s own ~1.4 s hold), so it can never show a guess. Alert sounds follow the app’s master mute.

Answered since rev 1

  1. UUIDs + layouts for reverse/crawl, ride mode, temps — all mapped above (svag-mini; walking-mode values confirmed on the EX via VP). hp/regen/TC turn out to be VP-only.
  2. Battery endianness/scale — little-endian, SOC is a whole percent (svag-mini parse_le_u16).
  3. Write/handshake before notifications? — no; both open-source clients just write the CCCD (startNotifications()) and frames flow. Bonding is the only gate (MITM + Secure Connections).
  4. Where does the PIN come from? — derivable from the VIN: SHA-256(VIN + "-19700101") (garmin-bridge).

Still open (for the EX-app dev)

  1. Vbus unit on 6004 bytes 4–5 — V, dV or mV?
  2. Does the MITM bond complete from a browser (Web Bluetooth) pairing dialog, or must Android bond first? (First on-bike run will settle it — watchdogs + PIN card are in place either way.)
  3. Typical notification rates on 6004 / 2004 / 1002?
  4. Can a second GATT client piggyback on the same bond while the stock app stays connected? garmin-bridge does exactly this from native Android — if Chrome can too, DingoNav's release/reclaim handoff becomes unnecessary.
  5. walking_mode values other than 0/8/12 — do any exist? (DingoNav currently treats unknown non-zero as crawl: safer loud than silent.)
  6. fault_bits (@6) semantics — worth surfacing beyond the alert severities?
